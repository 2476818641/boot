# 校园网检测项自查：TTL / UA / MAC

> 用途：怀疑校园网在"认出你"时，用**最小代价**判断它到底看了哪几项。
> 原则：能不动路由器的就不动；能 A/B 对照的就不猜；判据必须能双向验证。
>
> 实测记录截至 2026-09（本校：门户认证 RAAS，单账号 3 设备在线 / 账号总带宽 500Mbps）。
> 各校策略不同、同一学校也会换季调整 —— **先测再改**。

---

## 0. 先读这一节：用减法思维，别一上来就上最高规格

**本项目的核心结论：TTL / UA / MAC 这三项基础检测，覆盖了大约 90% 的实际环境。**

大量"校园网在跑 DPI / IPID 聚类"的说法来自**产品能力清单和技术文章**，而不是实地部署。
实际运维的取舍是"最小代价能交差"：

| 检测项 | 文章里的普及度 | 实际情况 | 为什么 |
|---|---|---|---|
| MAC / 认证绑定 | 高 | **几乎 100%** | 认证协议本身就要记录 NAS 端口/MAC，**不是为抓共享而设计** |
| 账号级限速 / 限设备数 | 高 | **很普遍** | 这是策略，不是检测；达标即可 |
| TTL 一致性 / 入站标记 | 中 | **中偏高** | NAT 后 TTL 不一致是操作系统差异的自然结果，顺手统计零成本；少数会主动惩罚（本项目就遇到） |
| 明文 UA | 中 | **中**（记录多、用于风控少） | HTTP 过审计网关本来就会记录，同样是顺手 |
| **IPID 聚类** | 中 | **少见** | 要专门写分析逻辑，运维很少做 |
| **DPI 分类限速** | 高 | **少见** | 贵、误报率高（虚拟机/双系统/热点/容器都会造出"多主机特征"）、要人维护规则库 |

### 0.1 两条行动准则

**准则一：先做"减法诊断"，不要叠加组件。**

遇到故障时，第一步是**停掉**可疑组件做 A/B 对照，而不是再装一个新组件：

```sh
# 例：怀疑 UA 改写插件，就先停掉它，然后立刻在客户端复测
/etc/init.d/UAmask stop
nft list chain inet fw4 UAmask_prerouting_before 2>/dev/null || echo "劫持链已清除"
# 客户端测试后再恢复： /etc/init.d/UAmask start
```

本项目实测价值：正是这一步**直接排除了 UA-Mask**（停掉后故障依旧），省掉了后面所有围绕它的猜测。

**准则二：按优先级递进，别跳过前两项。**

```
1. TTL（双向：出站统一 + 入站 TCP/UDP 补回）   ← 覆盖面最广，零代价，最容易踩
2. UA（统一人设，且与 TTL 自洽；443 豁免）      ← 只在明文 HTTP 场景有意义
3. MAC（固定 WAN MAC，或按额度让各设备自己认证）  ← 大多是"认证绑定"而非"抓共享"
4. 以上都排除后，才怀疑 IPID / DPI              ← 少见，且代价高
```

**为什么不能跳过**：TTL 与 UA 是"零代价、零副作用"的修复（本项目只修改 `ttl 0-2` 的异常值）；
而重型方案（用户态全量转发、代理内核、隧道封装）会引入 CPU 开销、稳定性风险，
甚至在配置不当时直接断网 —— **先花 5 分钟做前两项，能省下后面所有的折腾。**

### 0.2 如果前两项做完仍然不行

那才需要考虑 **IPID 聚类** 或 **DPI（TLS 指纹 / SNI / 协议分类）**。

**本项目不做这两块的实现**，原因：

- **IPID**：nft 做不到（改 IPID 必须重算 IP 头校验和，没有字段写入语法），只能走 eBPF/TC 或用户态 ——
  代价是"所有 TCP 进用户态转发"，会拖累加速器/Steam/P2P，停服务时还容易因规则残留断网；
  **更划算的解法是走隧道**（代理或 EasyTier 都可以）：多设备痕迹合并成"路由器本机一条流"，
  IPID 检测从源头失去依据，同时顺带解决共享检测与载荷类 DPI
- **DPI**：需要代理协议本身抗识别（VLESS+Reality / NaiveProxy 这一档）、一台服务器、
  以及额外的 CPU 开销；且**流量体量与统计特征这一层绕不过**（持续向陌生境外 IP 打大量加密流量本身就是特征）

> 效果与选型请自行了解，本文只负责把"哪一层值得先做"讲清楚。

## 1. 先建立正确的心智模型：客户端流量有三条路

排查走偏，多半是把这三条当成一条：

| 路径 | 谁在处理 | 是否转发 | 是否减 TTL | 典型表现 |
|---|---|---|---|---|
| **A 本地投递** | 路由器自己的连接（路由器上 `curl`） | 否 | **否** | 一切正常 |
| **B 本机中转** | 被 REDIRECT 到本机端口的流量（UA 改写插件的 80 端口、SOCKS 代理等） | 否（由路由器重新发起） | **否** | 看起来"通" |
| **C 真正的 NAT 转发** | 客户端 → 路由器 NAT → 校园网关 | 是 | **是** | 风控打的就是这里 |

由此产生三个致命假象：

- **"HTTP 能开"是假象** —— 80 端口被插件 REDIRECT 到本机中转，走的是路径 B，从未经过网关的转发检查
- **"ping 通"是假象** —— ICMP 不在标记范围内（实测入站 ICMP 的 TTL 正常 50）
- **"路由器能上网"是假象** —— 那是路径 A

**结论：`ping` 通 ≠ 网络正常；HTTP 通 ≠ NAT 转发通。判断客户端连通性必须测 HTTPS 与 UDP。**

## 2. TTL —— 两个方向，一次抓包 + 一次 ping

### 1.1 判"入站被标记"（最常见，也是本项目踩到的坑）

```sh
# 路由器上；同时在客户端访问任意 HTTPS 站点
tcpdump -ni wan -c 6 -vv 'tcp[tcpflags] & (tcp-syn|tcp-ack) == (tcp-syn|tcp-ack)'
```

看 `ttl` 字段：

| 抓到 | 结论 |
|---|---|
| 多个不同站点的 SYN-ACK 都是 **`ttl 1`** | **实锤**：不可能全世界服务器都用 TTL=1，是网关改的 |
| `ttl 50-60` | 入站未被做手脚 |

**为什么 `ttl 1` 致命**：Linux 转发时 TTL 减 1 → 归零 → 内核直接丢弃 → 客户端只会一直重发 SYN，直到 21 秒超时。表现为**客户端全挂、路由器自己却完全正常**。

同理抓 UDP：

```sh
tcpdump -ni wan -c 6 -vv 'udp and not port 53'
```

**TCP 与 UDP 都要看** —— 本项目实测：只修入站 TCP 时网页恢复、**游戏（LoL/Steam/ARK）仍然全挂**；补上 UDP 才恢复。

### 1.2 判"出站按 TTL 风控"（不动路由器，最轻量）

```cmd
:: 电脑上；Windows 的 ping 默认 TTL=128，用 -i 指定
ping 223.5.5.5
ping -i 64 223.5.5.5
ping -i 100 223.5.5.5
```

| 结果 | 结论 |
|---|---|
| 默认通、`-i 64` **不通** | **出站按 TTL 过滤**（只放行人设值）→ 必须统一出站 TTL |
| 三个都通 | 出站不看 TTL，只需修入站 |

### 1.3 A/B 对照（有代价：可能掉认证）

```sh
mv /etc/nftables.d/10-ttl-fix.nft /root/ && fw4 reload   # 之后客户端出站 TTL 变成 127
# 测速/浏览，观察是否掉认证或降速
mv /root/10-ttl-fix.nft /etc/nftables.d/ && fw4 reload   # 恢复
```

### 1.4 对策

```nft
# /etc/nftables.d/10-ttl-fix.nft（fw4 会自动包含进 table inet fw4）
chain ttl_fix {                     # 出站：统一成人设值（UA 说 Windows 就 128）
    type filter hook postrouting priority mangle + 1; policy accept;
    oifname != { br-lan } ip ttl set 128
    oifname != { br-lan } ip6 hoplimit set 128
}
chain ttl_fix_in {                  # 入站：把被改坏的补回来，TCP/UDP 都不能少
    type filter hook prerouting priority mangle; policy accept;
    iifname "wan" ip protocol tcp ip ttl 0-2 ip ttl set 64
    iifname "wan" ip protocol udp ip ttl 0-2 ip ttl set 64
}
```

```sh
fw4 reload
nft list ruleset | grep -c 'ttl set'   # 期望 3 处（出站 ttl / 出站 hoplimit / 入站 tcp+udp 各算一处时以实际为准）
```

- **只匹配 `ttl 0-2`**：正常互联网包是 50-60，不会被碰到；`ttl 1` 在正常路径上不可能出现 → 零副作用
- **改前必须 `nft -c` 干跑**：`/etc/nftables.d/` 里语法一错，`fw4 reload` 整体失败、防火墙起不来

## 3. UA —— 只有明文 HTTP 能测，全靠 A/B 对照

### 2.1 看有没有被审计／注入

```sh
tcpdump -ni wan -A 'tcp port 80 and not host <你的网关IP>' | grep -iE "user-agent|302|script|portal"
```

出现 302 跳门户、或页面被注入脚本 → 明文 HTTP 在审计链路上。

### 2.2 A/B 对照：同一 URL 换 UA

```sh
for ua in "Mozilla/5.0 (Windows NT 10.0; Win64; x64)" "Mozilla/5.0 (Linux; Android 14)" "curl/8.9"; do
  printf '%-42s ' "$ua"
  curl -s -o /dev/null -w '%{http_code}  %{time_total}s\n' -A "$ua" \
    http://connect.rom.miui.com/generate_204
done
```

| 结果 | 结论 |
|---|---|
| 状态码/耗时**明显不同**（如 Android 被 302 到门户、或超时） | **UA 参与风控** |
| 三者一致 | UA 只进审计日志，不参与放行判断 |

**判读要点**：明文 HTTP 里的 UA **一定被记录**（审计必然）；要判断的是"**是否用于风控**"，所以必须 A/B 对照，不能只看"日志里有"。

### 2.3 对策

- 统一 UA 人设（例如全部伪装成同一台 Windows PC）
- **必须与 TTL 自洽**：UA 说 Windows 就 128，说 Android/Linux/macOS 就 64
- **443 要豁免**：TLS 里没有明文 UA，劫持它只增加延迟与故障面
- UA 改写插件要开"非 HTTP 目标自动卸载"，并把判断延迟降到 2 秒左右（默认 10 秒会让首次连接直接超时）

## 4. MAC —— 看认证报文 + 改 MAC 对照

### 3.1 最轻量：认证报文里有没有 MAC 字段

```sh
tcpdump -ni wan -A 'tcp port 80 and host <门户IP>' | grep -oE "(mac|macaddr|nasid|acname)=[^&]*"
```

出现 `mac=` → **账号与 MAC 绑定**（换设备即需重认证）。

### 3.2 决定性但会掉线：改 WAN MAC

```sh
uci set network.wan.macaddr='02:00:00:00:00:01'
uci commit network && /etc/init.d/network reload
```

| 结果 | 结论 |
|---|---|
| 立刻掉线／要求重新认证 | **绑定 MAC** |
| 照常上网 | 按 **IP 认证**（NAT 后共享，最宽松） |

恢复：

```sh
uci -q delete network.wan.macaddr && uci commit network && /etc/init.d/network reload
```

顺带看 DHCP 是否按 MAC 固定分配 IP：

```sh
ifstatus wan | grep -E 'ipv4|macaddr'
```

### 3.3 对策

- WAN MAC 克隆成首次认证那台设备的 MAC，并**保持固定**（别乱改）
- 单账号设备额度有限（本校 3 台）→ 让**路由器占 1 个额度**，其余设备按需直连认证

## 5. 三者联动：矛盾才是最大的破绽

| 检测点 | 判定逻辑 | 自洽要求 |
|---|---|---|
| TTL | 出站是否等于人设值；**同一源 IP 出现多个不同 TTL = 后面有第二台设备** | 出站统一 128，入站补回 |
| UA | 明文 UA 的种类数 ≈ 设备种类数；Android UA 反复出现 = 共享嫌疑 | 全部统一成同一人设 |
| MAC | 账号绑定 MAC；MAC 频繁变化 = 换设备 | MAC 固定 |

**三项各自"正常"、合起来是明牌**：UA 说 Windows + TTL 是 64 + MAC 每次变。
正确顺序：**先确定人设（一台 Windows PC），再让三项全部对齐**。

## 6. 五分钟速查（按顺序）

```sh
# 1. 入站 TCP 是否被改（看 ttl 字段）—— 有 ttl 1 就必须修
tcpdump -ni wan -c 6 -vv 'tcp[tcpflags] & (tcp-syn|tcp-ack) == (tcp-syn|tcp-ack)'

# 2. 入站 UDP 是否被改 —— 缺这条 = 网页正常但游戏全挂
tcpdump -ni wan -c 6 -vv 'udp and not port 53'

# 3. 出站是否按 TTL 过滤（在电脑上跑）
#    ping 223.5.5.5   对比   ping -i 64 223.5.5.5

# 4. UA 是否参与风控（换 UA 请求同一 HTTP URL，看状态码/耗时）

# 5. MAC 是否绑定（看认证报文有无 mac= 字段；改 MAC 对照要挑不影响别人的时间）
```

> ⚠️ 第 5 项的"改 MAC 对照"**必然导致掉线重认证**；第 1、2 项抓包无影响。避开上课/用网高峰。

## 7. 诊断决策树

```
路由器能上网，客户端不能
├─ HTTPS 挂、HTTP 通、ping 通        → 入站 TTL 被标记（先补 TCP）
├─ 网页好了但游戏仍挂                → 入站 UDP 也被标记（再补 UDP）
├─ 客户端 UDP 直接超时（nslookup 223.5.5.5 也超时）
│                                    → 网关挡 UDP 或双重 NAT → 考虑中继/加速器
└─ 全都正常但游戏仍不行              → 才轮到查 DPI / 加速器
```

**别忘的两条**：

- UA 类改写插件**只碰 TCP**（nft 规则写死 `ip protocol tcp`），UDP 根本不经过它 → "停掉插件问题依旧"是必然，不要往那个方向查
- 先修 TTL，再谈加速器/隧道（本项目实测：TTL 补齐后 LoL/Steam/ARK 直接可用，**没有 DPI 阻断**）

## 8. 没有 tcpdump 时的等价手段（nft 计数器）

```sh
nft insert rule inet fw4 prerouting iifname "br-lan" tcp dport 443 counter   # 客户端发出
nft insert rule inet fw4 postrouting oifname "wan"  tcp dport 443 counter   # NAT 后发出
nft insert rule inet fw4 prerouting iifname "wan"   tcp sport 443 counter   # 回程
nft reset counters table inet fw4
# 客户端重试一次后看计数
nft list chain inet fw4 prerouting | grep -B2 counter
fw4 reload    # 清理临时计数器规则
```

| 客户端发出 | NAT 后发出 | 回程 | 结论 |
|---|---|---|---|
| 有 | **0** | 0 | 路由器内部丢弃（本地规则） |
| 有 | 有 | **0** | 上游网关丢弃 |
| 有 | 有 | 有 | 回程/NAT/conntrack 问题 |

## 9. 以上都确认无误、问题依旧：该考虑 DPI 与 IPID 了

走到这一步的前提是：**前面的 TTL（出站 + 入站 TCP/UDP）、UA、MAC 都已经验证正确**，
抓包也确认过"客户端经 NAT 的包确实出去了、回包也确实回来了"。

如果仍然不通，那就不是"基础检测层"能解释的问题了，需要往这两类进阶手段上想：

| 手段 | 特征 | 为什么前面那些招数失效 |
|---|---|---|
| **IPID 聚类** | 同一源 IP 出现多条互不相关的 IPID 递增序列 → 判定后面有多台设备 | 它看的是 **IP 头部的统计特征**，与你伪造的 UA/TTL 无关；加密、换端口都挡不住 |
| **DPI** | TLS 指纹（JA3/JA4）、SNI、协议与心跳指纹、报文长度分布 → 认出设备类型/应用类别 | 它看的是 **载荷与行为特征**；UA 统一了也没用，因为加密流量里还有别的指纹 |

**本项目不做这两块的实现**，原因在 §0 已经说明（IPID 用 nft 做不到、需 eBPF/TC 或用户态全量转发；
DPI 需要抗识别的代理协议 + 服务器，且流量体量这一层绕不过）。

> 请自行询问 AI、查阅其他文档或项目，并结合本文 §0 的优先级判断值不值得投入。

**一个可复用的思路**（不涉及具体实现）：这两类手段的共同依据都是"网关能看到 NAT 后面多台主机的痕迹"。
把多设备流量收进一条**由路由器本机发起**的隧道（代理或虚拟局域网都可以），这些痕迹就会合并成
"路由器一条流"，IPID 与大部分载荷型 DPI 的判据随之消失；代价是隧道自身的特征、CPU 开销，
以及**流量体量与统计特征这一层仍然绕不过**。

## 10. 本项目实测到的风控特征（2026-09）

| # | 特征 | 证据 | 应对 |
|---|---|---|---|
| 1 | 入站 **TCP** TTL 被改成 1 | 5 个站点 SYN-ACK 全为 `ttl 1` | `ttl_fix_in` 补回 64 |
| 2 | 入站 **UDP** 同样被标记 | 只修 TCP 时游戏全挂，补 UDP 后恢复 | 同链加 `ip protocol udp` |
| 3 | 路由器自身流量不被标记 | 本机 curl 一切正常 | 隧道/代理端点放在路由器上 |
| 4 | **ICMP 不参与** | 客户端 ping 通、入站 TTL 正常 | 别拿 ping 当判据 |
| 5 | NAT 类型 **NAT3（Port-Restricted）** | 直连实测 + EasyTier 自测 | 隧道端点放路由器保持单层 NAT3 |
| 6 | 上游还有一层 **CGNAT** | WAN 是私有地址 10.30.x.x | 入站 P2P 只能靠中继 |
| 7 | 认证粒度是**源 IP**（NAT 后共享） | 路由器认证后全屋可上网 | 内网设备零配置 |
| 8 | 未认证时放行集合极小 | 认证状态一掉客户端就残 | 开机 + 网口 up + cron 每 5 分钟兜底 |
| 9 | **无针对游戏的 DPI 阻断** | 补 UDP TTL 后游戏直接可用 | 先修 TTL，再谈加速器 |
| 10 | 单账号 **3 设备 / 总 500Mbps** | 运营商口径 | 路由器占 1 个额度；硬件性能不是瓶颈 |

**推测（未验证，欢迎对照实验）**：
第 3 与 1/2 组合指向"共享检测的惩罚动作" —— 同一源 IP 上出现矛盾的 TTL（客户端经 NAT 后 127、路由器自己 64）→ 判定后面有第二台设备 → 把该 IP 的入站应答 TTL 改成 1 使其静默失败。
它能解释全部观察（本机豁免、纯本机中转方案不受影响、只影响转发路径），但**尚无对照实验证明**。

## 11. 合规与安全提醒
